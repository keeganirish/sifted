# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Sifted is deterministic multi-sensor track fusion: a C++20 daemon (`sifted_fusiond`) ingests radar/camera/ADS-B measurements over UDP, associates and filters them into tracks, and publishes snapshots over WebSocket to a Leaflet operator map. Python simulators feed it; a Python launcher ties everything together behind a local control API.

The fusion service is Linux/POSIX software. On Windows, build and run it inside WSL (the Windows installer and `sifted.cmd` do this); the Windows-side scripts are only `install.cmd`, `scripts/windows/*.ps1` and `sifted.cmd`.

## Commands

```bash
cmake --preset dev && cmake --build --preset dev && ctest --preset dev   # Debug, -Werror
ctest --preset dev -R 'EventLog\.'                  # subset by gtest name (gtest_discover_tests)
build/dev/tests/sifted_tests --gtest_filter='Reorder.*'   # or run the gtest binary directly
cd sim && PYTHONPATH=. python3 -m unittest discover -s tests   # Python tests (also run by ctest as sim_wire_python)
cd sim && PYTHONPATH=. python3 -m unittest tests.test_impair   # single Python test module
```

Presets: `dev`, `release` (benchmarks), `asan` (ASan+UBSan), `tsan`, `fuzz` (Clang+libFuzzer), `app` (what `install.sh` builds: Release, no -Werror, no tests). Build dirs are `build/<preset>`. Add `-DSIFTED_FETCH_DEPS=ON` if Eigen/GoogleTest aren't installed. TSan failing with "unexpected memory mapping" on WSL2 is environmental: `sudo sysctl vm.mmap_rnd_bits=28`.

Formatting is enforced in CI with clang-format 18 over `src tests fuzz benchmarks`:
```bash
find src tests fuzz benchmarks -name '*.cpp' -o -name '*.hpp' | xargs clang-format-18 --dry-run -Werror
```

Fuzzing (six targets, corpora in `fuzz/corpus*`; CI pairs each target with its corpus, see `.github/workflows/ci.yml`):
```bash
cmake --preset fuzz && cmake --build --preset fuzz
build/fuzz/fuzz/fuzz_engine build/fuzz-work/engine fuzz/corpus_engine -max_total_time=60
```

Running the app: `./sifted` (launcher, serves http://127.0.0.1:8000/), `./sifted --check`. Running daemon/simulators by hand, benchmarks, ADS-B setup and the launcher's control API are documented in `docs/development.md`.

## Architecture

Pipeline: UDP rx thread (size check → per-source rate limit → strict decode → recv timestamp) → `BoundedQueue` → engine thread running `net::Pipeline` (dedup → clock gate → reorder stage → scan assembly → `Engine`: gate/associate → estimate → track store) → output lines + snapshots → WebSocket thread (publishes latest snapshot only). Every frame and tick is written to the event log with its receive time. Thread ownership table is in `docs/design.md` §2.

Library split (`src/CMakeLists.txt`) is a deliberate boundary:
- `sifted_core`: the deterministic core — no threads, sockets or wall clock. Includes `core`, `wire`, `estimation`, `association`, `store`, `replay`, and the *pure* parts of `net` (ingest pipeline, dedup, impairment model, snapshot).
- `sifted_net`: the OS-facing edge (UDP, WebSocket, SHA-1, rate limiter, system clock). Only the daemon and tests link it. Don't pull socket/clock/thread code into `sifted_core`.

### Determinism contract (most important invariant)

A recorded run must replay **bit-for-bit** identically (`docs/design.md` §3, ADR 0002/0005). When changing core code:
- Time is an input (`Clock`/`Timestamp`); only the live edge reads the machine clock, and what it reads is recorded. Timestamps and ids are integers.
- Engine is single-threaded and a pure function of ordered input.
- Never add `-ffast-math`; `-ffp-contract=off` is required (`cmake/SiftedOptions.cmake`).
- No iteration over hash/address-ordered containers where order affects output; break ties by id.
- Any parameter that changes output must live in `PipelineConfig` and be written to the event log header.
- Randomness (impairments, faults, workloads) is seeded SplitMix64; the impairment model is bit-identical between C++ (`src/sifted/net/impairment.cpp`) and Python (`sim/sifted_sim/impair.py`).
- Performance shortcuts must not change results (e.g. the gate screen is checked against an engine without it, including by `fuzz_engine`).

### Cross-language contracts and fixtures

- Wire format v1 (ADR 0001): C++ `src/sifted/wire/codec.*` and Python `sim/sifted_sim/wire.py` must both reproduce the hand-derived `tests/fixtures/measurement_bearing_only_v1.hex`. Changing that fixture means bumping the wire version.
- `tests/fixtures/impairment/golden.txt` is shared by C++ and Python impairment tests; regenerate with `cd sim && python3 -m sifted_sim.impair --write-golden ../tests/fixtures/impairment/golden.txt`.
- Scenario fixtures (`tests/fixtures/scenarios/<name>/`) are generated by the simulator and drive ground-truth regression tests; after changing a scenario or simulator, regenerate (command in `tests/fixtures/README.md`) and re-check baselines in the regression test headers.

### Untrusted input

Every parser of external input (wire frames, event log + header, sensor table, WebSocket, engine input) has a fuzz target in `fuzz/`. A new parser of untrusted input should get one too. See `docs/threat-model.md`.

### App layer

- `app/launcher.py` (standard-library Python only, listens on 127.0.0.1 only): serves `web/`, exposes a JSON control API (`POST` requires header `X-Sifted: 1` and the launcher's own `Host`), spawns daemon / impairment proxy / sender / ADS-B adapter as child processes, records runs to the data folder (`~/.local/share/sifted`, macOS `~/Library/Application Support/Sifted`, or `$SIFTED_DATA_DIR`) and verifies replays.
- `web/`: plain HTML/CSS/JS, Leaflet vendored; **no build step**. Must be served over HTTP (not `file://`) for OSM tiles.
- `sim/`: standard-library Python; no third-party dependencies.
- `install.sh` must stay idempotent (CI runs it twice on Ubuntu and macOS). Shell scripts need LF endings.

Design decisions are recorded in `docs/adr/0001`–`0011`; consult the relevant ADR before changing wire format, sensor table, association/lifecycle, event log, networking, tangent-plane origin, impairment model, out-of-order policy, fault handling or benchmark method.
